### 1.1 Blockers

#### B1: Prompt immutability conflicts with other requested behavior

The stored prompts contain:

- `You are read-only; do not attempt writes.`
- Literal `paper/` paths in several task bodies.
- `../style/latex_style_guide.txt` in `refine-tex-directory`.
- Meta-agent instructions saying green and yellow agents must remain wholly read-only.

Those instructions conflict with:

- Allowing writes under `agent-data/`.
- Renaming `paper/` to `papers/template/`.
- Resolving mathematical targets from any paper.

Decision-ready options:

1. **Handler-owned runtime context, recommended:** preserve every stored task body except `merge`; at runtime, the handler removes the legacy access preamble, adds the new permission preamble, and supplies resolved repository, paper, style-guide, and mathematical-target paths. Treat task bodies as immutable and access/path context as handler metadata.
2. Permit mechanical access-line and path-only edits to affected prompts while leaving all substantive task instructions unchanged.
3. Retain a root `paper` symlink or junction to `papers/template`. This is not recommended because Git and native Windows symlink behavior are not reliably portable and the alias weakens path-boundary validation.

The requirements below assume option 1.

#### B2: No local 8B runtime or exact model is available

No `ollama`, `lms`, or `lmstudio` executable was found on `PATH`, and no exact 8-billion-parameter model identifier is configured. The installed `codex-cli 0.154.0` exposes `--oss`, `--local-provider ollama|lmstudio`, and `--output-schema`, but that does not install a backend or model.

Before the research watcher can be accepted, select:

- Local backend: `ollama` or `lmstudio`.
- Exact installed model identifier.
- Evidence that the selected model has 8B parameters.

The handler must not silently substitute a differently sized model.

## 3. Scope

### 3.1 In scope

- Move the existing manuscript to `papers/template/`.
- Support any number of direct child paper directories under `papers/`.
- Add a paper-name parameter to `merge`.
- Resolve TeX labels across all papers and reject global conflicts.
- Allow mathematical target parameters to identify either a TeX label or a Markdown note.
- Add unrestricted user-authored Markdown storage under `markdown/`.
- Split handler implementation into documented modules under `metasrc/`.
- Leave only the handler entrypoint `agent.py` as root-level Python implementation code.
- Abstract model execution behind a provider interface.
- Give agents write access to `agent-data/` while keeping other repository paths read-only unless explicitly granted by risk policy.
- Move durable memory to `agent-data/memory/`.
- Run maintenance before each actual model invocation.
- Move PDF cache implementation into `metasrc/` and make it the initial maintenance task.
- Add an editor-independent Markdown save watcher.
- Generate deterministic, non-interpretive research JSON records using deterministic preprocessing plus a local 8B model.
- Update documentation, migration behavior, tests, and ignore rules.

### 3.2 Non-goals

- Rewriting substantive task prompts other than `merge`.
- Automatically creating new papers.
- Parameterizing every manuscript-wide agent by paper name. Unparameterized workflows continue to target `template`.
- Combining bibliography files or build outputs across papers.
- Treating labels as local to a paper; requested behavior requires repository-wide uniqueness.
- Enforcing a Markdown dialect, heading structure, front matter, prose style, or note organization.
- Generating summaries, claims, conclusions, truth assessments, sentiment, or support/refutation relationships from notes.
- Adding embeddings, vector search, or a hosted indexing service.
- Changing existing report naming or yellow-output destinations.
- Adding provider-specific logic to agent definitions.

## 6. Functional Requirements

### 6.1 Multi-paper repository

#### MP-1 Paper discovery

The handler must discover papers by enumerating direct children of `papers/` and accepting only directories that:

- Are not symlinks.
- Match the `paper_name` pattern.
- Contain a regular `main.tex`.
- Resolve inside the active workspace’s `papers/` directory.

Discovery order must be case-insensitive lexical order with the original path as the tie-breaker.

#### MP-2 Paper names

`paper_name` must:

- Match `[A-Za-z0-9][A-Za-z0-9_-]*`.
- Reject dots, slashes, backslashes, drive prefixes, `.` and `..`.
- Resolve to an existing paper.
- Reject case-insensitive ambiguity on case-sensitive filesystems.

#### MP-3 Merge interface

`agents/merge.json` must declare:

```json
{
  "params": {
    "paper": {
      "type": "paper_name",
      "required": false,
      "default": "template"
    }
  },
  "write_scope": "papers/{paper}"
}
```

Observable commands:

```powershell
python agent.py --agent merge
python agent.py --agent merge --p "paper=template"
python agent.py --agent merge --p "my-paper"
```

The merge prompt is the only task-specific prompt that may be rewritten. It must:

- Name the selected paper using `{paper}`.
- Treat the selected paper directory as its only manuscript write target.
- Read staged input from the repository-root `merge/`.
- Read the shared style guide from the repository-root `style/`.
- Build from the selected paper directory.
- Preserve the existing completeness, audit, and build requirements.

Missing, empty, or invalid staging input must retain the current stop-without-edits behavior.

#### MP-4 Red write scope

`write_scope` becomes a validated relative path template rather than the fixed literal `paper`.

It may interpolate only a `paper_name` parameter. After rendering it must:

- Resolve beneath `papers/`.
- Resolve to exactly one discovered paper.
- Reject symlink traversal.
- Be included in the provider’s writable roots only for that invocation.

`refine-tex-directory` retains no new parameter and receives `papers/template/` as its resolved write scope.

#### MP-5 Build behavior

Each paper is independently built from its own directory:

```powershell
cd papers/<paper>
latexmk -pdf -interaction=nonstopmode -file-line-error main.tex
```

No shared auxiliary directory or cross-paper build is introduced.

### 6.2 Cross-paper labels and Markdown mathematical targets

#### MT-1 New input type

Add `math_target` to the definition schema and migrate the `id` parameter of:

- `conjecture-evaluator`
- `proof-engine`
- `proof-reviewer`
- `proof-revisor`

No task-body text in those definitions changes.

#### MT-2 Markdown branch

If the supplied value ends in `.md` or `.markdown`, the handler must:

- Require a repository-relative path.
- Resolve it under `markdown/`.
- Require an existing readable regular file.
- Reject traversal and symlink escape.
- Perform no Markdown syntax, heading, front-matter, math-delimiter, or style validation.
- Return a resolved target with `kind = "markdown_file"` and the canonical repository-relative path.

The handler-owned runtime context must tell the model that the `id` value denotes the complete Markdown file rather than a TeX label.

#### MT-3 TeX-label branch

All other values must:

- Match the existing TeX-label key pattern.
- Trigger construction of a complete label index from every `*.tex` file beneath every discovered paper.
- Use the existing ordinary-comment stripping behavior.
- Include labels in example files, preserving current scanning scope.

Before resolving the requested label:

1. If any label occurs more than once anywhere across all papers, reject the run and list every duplicate label and every `path:line`, sorted deterministically.
2. If the requested label does not exist, reject the run.
3. Otherwise return its unique `path:line`.

No model provider may be called after either rejection.

#### MT-4 Runtime target context

The handler must pass a typed target context to the provider:

```json
{
  "kind": "tex_label",
  "value": "thm:example",
  "path": "papers/example/chapters/result.tex",
  "line": 42
}
```

or:

```json
{
  "kind": "markdown_file",
  "value": "markdown/scratch/idea.md",
  "path": "markdown/scratch/idea.md",
  "line": null
}
```

This context is handler-owned. It must not be exposed as a new user parameter.

#### HM-1 Root entrypoint

Root `agent.py` must contain only:

- The import of `metasrc.cli.main`.
- `raise SystemExit(main())`.

It must contain no validation, provider, output, worktree, maintenance, or indexing implementation.

| `handlers/runs.py` | Run directories, metadata, logs, report reservation |

### 6.4 Model provider abstraction

#### PR-1 Provider contract

`providers/base.py` must define equivalent typed contracts for:

```text
ModelRequest
- prompt
- model
- reasoning
- working_directory
- writable_roots
- output_schema
- run_directory
- stream_output
- enable_event_log
- local_only

ModelResponse
- final_text
- provider_id
- model
- exit_code
- stdout_path
- stderr_path
- events_path

ModelProvider
- validate(request)
- invoke(request) -> ModelResponse
```

Provider implementations own model-name and capability validation. The orchestrator must not construct Codex-specific flags.

#### PR-2 Existing hosted behavior

`CodexCliProvider` must preserve:

- `gpt-5.6-sol` as the default model.
- Existing reasoning values and default `high`.
- Ephemeral execution.
- Final-message capture.
- Optional JSONL event capture.
- Live stdout and stderr streaming.
- Exit-code and missing-final-message failures.

#### PR-3 Permission profile

The Codex provider must use a custom permission profile extending read-only access and granting writes only to canonical absolute roots supplied in `ModelRequest.writable_roots`.

- Green/yellow: `agent-data/`.
- Red: `agent-data/` plus the selected paper.
- No invocation receives repository-root write access.
- Approval policy remains `never`.
- Network behavior remains unchanged from the existing agent risk policy.

The provider must reject missing, non-directory, symlinked, overlapping, or out-of-workspace writable roots before invoking Codex.

### 6.5 `agent-data/` and memory

#### AD-1 Writable area

All agents receive full write permission beneath `agent-data/` and read-only access elsewhere, subject to red-paper access.

The runtime access preamble must state the resolved paths explicitly. Legacy stored read-only lines must be removed from the rendered prompt before invocation so contradictory instructions are never sent.

#### AD-2 Memory migration

Move:

- `memory/ledger.yaml` to `agent-data/memory/ledger.yaml`.
- Every registered managed memory file to `agent-data/memory/`.

Update:

- `canonical_entry`.
- `storage.root`.
- Every registered `path`.
- Relevant evidence paths.
- Topology history with one migration event.
- `AGENTS.md` memory entrypoint.
- Agent-data permission and command-agent rules.

The existing protocol, record schema, correction history, and fallibility rules remain intact.

#### AD-3 Concurrency

Agents modifying durable memory must continue to reread the ledger and affected records immediately before writing. Handler execution does not serialize unrelated agents. Any irreconcilable concurrent memory change remains a task failure rather than a last-writer-wins update.

### 6.6 Pre-run maintenance

#### MA-1 Maintenance contract

Every actual provider invocation must call `MaintenanceRunner.run()` after configuration, input, path, and destination validation but immediately before `ModelProvider.invoke()`.

`--help` and `--validate-only` must not run maintenance.

A maintenance task returns:

```json
{
  "id": "pdf-cache",
  "status": "updated",
  "started_at": "ISO-8601 timestamp",
  "duration_ms": 124,
  "details": {
    "files": 3,
    "errors": 0
  }
}
```

Allowed statuses are `unchanged`, `updated`, and `failed`.

#### MA-2 Initial task

The only initially registered task is `pdf-cache`. It must call the migrated PDF cache implementation with:

- Root equal to the active repository or worktree root.
- Cache directory equal to `<root>/.pdf-cache`.
- Normal incremental behavior.
- Pruning enabled.
- No forced full verification.

#### MA-3 Failure behavior

A failed maintenance task must:

- Prevent the model invocation.
- Produce an `ERROR` exit.
- Record the task, error, and duration in the manager log and run metadata.
- Leave any prior valid cache manifest intact through atomic writes.

Parallel invocations must use an interprocess maintenance lock so that PDF cache refreshes do not race. Waiting invocations run the incremental check after acquiring the lock.

#### MA-4 Manual command

Expose:

```powershell
python agent.py --maintenance
```

This runs registered maintenance tasks without invoking an agent.

### 6.7 Markdown research database

#### RI-1 Source scope

Watch recursively beneath `markdown/` for regular `.md` and `.markdown` files. Ignore symlinks and all other suffixes.

No authoring-style assumptions are permitted. Notes may contain arbitrary headings, fragments, lists, prose, code, TeX, malformed Markdown, or no Markdown structure.

#### RI-2 Commands

Expose:

```powershell
python agent.py --watch-markdown --local-provider <ollama|lmstudio> --local-model <model-id>
python agent.py --reindex-markdown --local-provider <ollama|lmstudio> --local-model <model-id>
```

The watcher must:

- Index existing notes on startup.
- Poll without third-party filesystem dependencies.
- Debounce rapid changes.
- Confirm a file has stable size and modification time before reading.
- Hash content before deciding whether reindexing is required.
- Process the latest stable save once.
- Remove records and connections for deleted notes.
- Treat rename as delete plus create.

#### RI-3 Deterministic preprocessing

The handler, not the model, must:

- Decode the note as UTF-8, accepting an optional BOM.
- Normalize line endings to LF for indexing.
- Calculate SHA-256 of the normalized text.
- Assign `note_id = "note_" + first 24 lowercase hexadecimal characters of SHA-256(repository-relative source path)`.
- Divide the note into ordered, non-overlapping blocks using blank lines, fenced blocks, and a fixed maximum-character fallback.
- Assign segment IDs as `seg_0001`, `seg_0002`, and so on.
- Calculate zero-based, half-open Unicode code-point spans.
- Detect explicit Markdown links deterministically where syntactically recognizable.
- Sort arrays and JSON object keys canonically.

The model must not create identifiers or segment boundaries.

#### RI-4 Local 8B task

For each deterministic segment, the local model may return only zero to five exact topic spans from that segment.

It must not return:

- Summaries.
- Rephrasings.
- Claims or conclusions.
- Importance judgments.
- Truth or confidence judgments.
- Semantic relationship labels.
- Text not present in the note.

The model output schema is:

```json
{
  "segments": [
    {
      "ordinal": 0,
      "topic_spans": [
        {
          "start": 12,
          "end": 34
        }
      ]
    }
  ]
}
```

Offsets are relative to the supplied segment. The handler converts them to document offsets and rejects:

- Missing or duplicate ordinals.
- Out-of-range or reversed spans.
- Blank selections.
- More than five topics per segment.
- Output fields not in the schema.
- Any output not conforming to `model-output.schema.json`.

#### RI-5 Determinism controls

- Use temperature zero when supported.
- Use a fixed seed when supported.
- Record provider, exact model, model-size declaration, prompt version, and segmentation version.
- Cache successful model results by source hash, model, and prompt version.
- Do not invoke the model again for an unchanged cache key.
- Canonical JSON uses UTF-8, LF, two-space indentation, sorted keys, and one trailing newline.
- Canonical records contain no indexing timestamps or source filesystem timestamps.
- Reindexing identical content with identical configuration must produce byte-identical JSON.

#### RI-6 Degraded mode

If local inference fails or returns invalid data:

- Write a valid `deterministic_only` record using deterministic segments and no topic spans.
- Log the operational error separately.
- Never retain topic spans from an older source hash.
- Retry on the next save or manual reindex.
- Do not call a hosted provider as fallback.

#### RI-7 Connections

Normalize accepted topic text using Unicode normalization, case folding, internal-whitespace collapse, and surrounding-punctuation removal.

Create a candidate connection only when the same nonblank normalized topic occurs in at least two distinct notes. Connections must:

- Be labeled only `shared_topic_text`.
- Reference exact note, segment, and source spans.
- Never claim support, contradiction, dependency, causality, equivalence, or subject identity.
- Be sorted and assigned deterministic IDs from their normalized topic and ordered members.

## 7. Research Database Contracts

### 7.1 Per-note record

Location:

```text
agent-data/research/db/notes/<note-id>.json
```

Schema shape:

```json
{
  "schema_version": 1,
  "note_id": "note_4f7c2e6f4a28c82a692f6d31",
  "source": {
    "path": "markdown/example.md",
    "sha256": "full-lowercase-sha256",
    "character_count": 431,
    "line_count": 18
  },
  "indexer": {
    "status": "complete",
    "segmentation_version": 1,
    "prompt_version": 1,
    "provider": "codex-local",
    "local_provider": "ollama",
    "model": "selected-exact-model-id",
    "parameter_count_billion": 8
  },
  "segments": [
    {
      "id": "seg_0001",
      "span": {
        "start": 0,
        "end": 116
      },
      "topic_spans": [
        {
          "start": 14,
          "end": 37,
          "text": "exact source substring",
          "normalized": "exact source substring"
        }
      ]
    }
  ],
  "links": []
}
```

`indexer.status` is `complete` or `deterministic_only`.

For every stored topic:

```text
normalized_note_text[start:end] == text
```

must hold.

### 7.2 Manifest

Location:

```text
agent-data/research/db/manifest.json
```

It maps canonical source paths to note IDs, source hashes, record paths, and status. It contains no note prose.

### 7.3 Connections

Location:

```text
agent-data/research/db/connections.json
```

```json
{
  "schema_version": 1,
  "connections": [
    {
      "id": "connection_<deterministic-hash>",
      "type": "shared_topic_text",
      "topic": "normalized exact topic",
      "members": [
        {
          "note_id": "note_...",
          "segment_id": "seg_0001",
          "span": {
            "start": 14,
            "end": 37
          }
        }
      ]
    }
  ]
}
```

### 7.4 Atomicity

Write each changed record to a same-directory temporary file, flush it, and replace the destination atomically. Update order is:

1. Per-note records.
2. Connections.
3. Manifest last.

A reader seeing the new manifest must therefore be able to resolve every referenced record.

## 8. Execution Data Flow

### 8.1 Agent invocation

1. Parse CLI.
2. Load and validate agent definition.
3. Parse named and positional parameters.
4. Validate typed inputs.
5. Discover papers and build the global label index if required.
6. Resolve mathematical target, output destination, paper target, and writable roots.
7. Render stored prompt parameters.
8. Replace the legacy access preamble with handler-owned runtime access context.
9. Add resolved target and legacy path mappings without rewriting task instructions.
10. Create run directory and initial metadata.
11. Run maintenance.
12. Construct provider-neutral `ModelRequest`.
13. Invoke the selected provider.
14. Validate returned artifact.
15. Perform handler-owned atomic output write, unless direct output.
16. Finalize logs and result metadata.

### 8.2 Markdown save

1. Watcher detects a stable changed file.
2. Normalize and hash content.
3. Return without rewriting if manifest cache key is unchanged.
4. Build deterministic note ID and segments.
5. Invoke the selected local 8B provider using the strict output schema.
6. Validate every returned span against source text.
7. Fall back to deterministic-only data on failure.
8. Recompute affected lexical connections.
9. Atomically replace note, connection, and manifest records.
10. Emit a concise operational event without recording note contents.

## 9. Observable Failure Behavior

## 11. Security, Privacy, and Performance

### 11.1 Security invariants

- Repository root is never a writable root for a command agent.
- `agent-data/` is always writable to command agents.
- A red agent receives exactly one additional paper root.
- Yellow output writes remain handler-owned.
- All resolved roots undergo canonical containment and symlink checks.
- Markdown note text is treated as untrusted data.
- The local indexer runs without repository write tools; only the handler writes database JSON.
- Note content is never sent to a hosted model by the indexing workflow.
- Source PDFs remain accessible only through `.pdf-cache/` under the existing `AGENTS.md` policy.

### 11.2 Performance requirements

- Unchanged PDF maintenance remains metadata-fast.
- Label files are read once per validation and indexed in memory.
- Unchanged notes do not invoke the local model or rewrite JSON.
- Only connections involving changed or deleted notes need recomputation, although a full deterministic rebuild is acceptable initially if documented and tested.
- Watcher polling must avoid busy waiting; default interval should be at least 500 ms.
- Indexing must process one note at a time by default to avoid exhausting memory on an 8B local runtime.

### 11.3 Observability

Run metadata must record:

- Agent and risk.
- Provider and model.
- Workspace.
- Resolved paper.
- Resolved mathematical target kind and path.
- Writable roots.
- Maintenance results.
- Output destination.
- Success or failure.

Research operational logs must record:

- Source path.
- Source hash.
- Whether inference was invoked or cache reused.
- `complete` or `deterministic_only`.
- Duration.
- Error class and concise message.

They must not duplicate note contents or model prompts.

## 16. Risks

| Risk | Mitigation |
|---|---|
| Copying `template` creates duplicate labels | Merge remains usable, but label-target workflows fail clearly until labels are made globally unique |
| Agents overwrite shared memory concurrently | Preserve ledger reread-and-merge protocol; never use silent last-writer-wins |
| Custom permission configuration varies by Codex version | Require startup capability validation; document version validated against `0.154.0` |
| Runtime prompt adaptation obscures the stored prompt | Save the exact rendered prompt and resolved runtime context in each run directory |
| Local model emits fabricated topic strings | Accept offsets only; derive all stored text by slicing the source |
| Temperature-zero inference still varies | Cache by content/model/prompt version and canonicalize all accepted output |
| Watcher is not running | Document startup command and provide manual full reindex |
| Large or pathological notes overload the model | Deterministic bounded segmentation and sequential inference |
| Generated database becomes stale after manual deletion | Manifest reconciliation on watcher startup and full reindex |
| Research database causes Git churn | Ignore generated database while tracking source notes, schema, and documentation |
