## 3. Scope

### 3.1 In scope

- Move the existing manuscript to `papers/template/`.
- Support any number of paper directories directly beneath `papers/`.
- Require an explicit paper input whenever an invocation operates on a specific paper; do not use `template` as an implicit target.
- Resolve that input to one canonical paper directory and use the resolved path for prompts, working directories, validation, builds, and permissions.
- Resolve TeX labels across all papers and reject repository-wide label conflicts.
- Allow the four mathematical target parameters to identify either a TeX label or a whole Markdown note.
- Treat `markdown/` as the complete research database for now: a folder of user-authored Markdown notes with no derived index.
- Split handler implementation into documented modules under `metasrc/`, leaving root `agent.py` as the entrypoint.
- Abstract model execution behind a provider interface.
- Give every command agent write access beneath `agent-data/`; give manuscript-writing agents additional write access only beneath their resolved paper directory.
- Move durable memory to `agent-data/memory/` and explain correct `agent-data/` use in `AGENTS.md`.
- Make mechanical stored-prompt edits required by the new paths and permissions while preserving substantive task instructions.
- Run generic registered maintenance immediately before every actual provider invocation.
- Move the PDF cache implementation into `metasrc/maintenance/` and register PDF-cache maintenance as the initial default task.
- Update documentation, migration behavior, tests, and ignore rules.

### 3.2 Non-goals

- Any research JSON schema, manifest, per-note record, connection file, or generated research database.
- A local 8B model, local-provider flags, note segmentation, topic extraction, semantic matching, embeddings, vector search, or hosted indexing.
- A file watcher, save hook, research store, research lock, or reindex command.
- Extracting or identifying conjectures, objects, claims, or topics inside Markdown notes.
- Rewriting substantive prompt tasks, evidence standards, reasoning workflows, or output contracts.
- Automatically creating new papers.
- Combining bibliography files or build outputs across papers.
- Treating labels as local to a paper; label uniqueness remains repository-wide.
- Enforcing a Markdown dialect, heading structure, front matter, prose style, mathematical delimiter style, or note organization.
- Changing existing report naming, yellow-output destinations, detached execution, batch semantics, or worktree policy except where resolved paper paths must be carried through them.
- Adding provider-specific fields to agent definitions.

## 6. Functional Requirements

### 6.1 Multi-paper repository and explicit paper inputs

#### MP-1 Paper discovery

The handler must discover papers by enumerating direct children of `papers/` and accepting only directories that:

- Are not symlinks.
- Match the `paper_name` pattern.
- Contain a regular `main.tex`.
- Resolve inside the active repository or worktree's `papers/` directory.

Discovery order must be case-insensitive lexical order with the original path as the tie-breaker.

#### MP-2 Paper names

`paper_name` must:

- Match `[A-Za-z0-9][A-Za-z0-9_-]*`.
- Reject dots, slashes, backslashes, drive prefixes, `.` and `..`.
- Resolve to an existing discovered paper.
- Reject case-insensitive ambiguity on case-sensitive filesystems.

Validation must return a typed resolved paper rather than an unchecked string:

```json
{
  "name": "example",
  "path": "papers/example",
  "main_tex": "papers/example/main.tex"
}
```

The in-memory object must also carry canonical absolute paths for permission construction. User-facing metadata and prompts use canonical repository-relative paths where possible.

#### MP-3 Paper-dependent agent definitions

The following manuscript-wide definitions must add a required `paper` parameter:

- `merge`
- `refine-tex-directory`
- `evaluate-references`
- `prelim-finder`
- `todo-reviewer`

The parameter schema is:

```json
{
  "paper": {
    "type": "paper_name",
    "required": true
  }
}
```

No definition may default this parameter to `template` or any other paper. Observable commands include:

```powershell
python agent.py --agent merge --p "template"
python agent.py --agent refine-tex-directory --p "paper=my-paper"
python agent.py --agent evaluate-references --p "paper=my-paper"
```

Omitting `paper` from one of these invocations is an input error and must not run maintenance or a provider.

#### MP-4 Target-driven mathematical agents

The four mathematical agents keep their task-local `id` parameter and gain a conditional paper input:

```json
{
  "id": {
    "type": "math_target",
    "required": true
  },
  "paper": {
    "type": "paper_name",
    "required": false
  }
}
```

`proof-revisor` retains `changes` in its existing relative order; `paper` is appended after existing parameters. The cross-field contract is:

- TeX-label `id`: `paper` is required.
- Markdown-file `id`: `paper` must be omitted.

Named parameters are the recommended form for the label branch:

```powershell
python agent.py --agent proof-reviewer --p "id=thm:convergence" --p "paper=my-paper"
python agent.py --agent proof-reviewer --p "id=markdown/ideas/convergence.md"
```

#### MP-5 Resolved path use

After paper validation, the handler must use the resolved paper object consistently:

- Render a handler-owned runtime context containing the paper name and canonical repository-relative path.
- Resolve any dynamic red `write_scope` from that same object.
- Use the resolved paper as the working directory for manuscript-writing agents.
- Use the resolved paper for manuscript scans, bibliography paths, build commands, warnings, run metadata, and permission roots.
- Pass the resolved paper context to read-only manuscript agents even when their process working directory remains the repository root.

The handler must not derive a paper from `papers/template/`, the current process directory, or a prompt literal. It must not accept a second resolution path that could disagree with the validated object.

For red definitions, `write_scope` becomes the validated template `papers/{paper}`. It may interpolate only the declared `paper_name` parameter. The rendered path must resolve to the same paper object already selected by input validation; string interpolation alone is not sufficient validation.

#### MP-6 Prompt path migration

Stored references to the old `paper/` root must be changed mechanically to the resolved paper target. Examples include:

- `paper/refs.bib` becomes the resolved paper target's `refs.bib`.
- `paper/chapters/` becomes the resolved paper target's `chapters/`.
- “under `paper/`” becomes “under the resolved paper directory.”
- Merge staging and the shared style guide use handler-resolved repository-root `merge/` and `style/latex_style_guide.txt` paths; they must not rely on `../` from a nested paper directory.

Do not replace old paths with `papers/template/`. Definition validation or tests must reject hard-coded `papers/template/` in paper-dependent prompts.

#### MP-7 Build behavior

Each paper is independently built from its resolved directory:

```powershell
cd papers/<paper>
latexmk -pdf -interaction=nonstopmode -file-line-error main.tex
```

No shared auxiliary directory or cross-paper build is introduced. Missing, empty, or invalid merge staging input retains the current stop-without-edits behavior.

### 6.2 Cross-paper labels and whole-file Markdown targets

#### MT-1 New input type

Add `math_target` to the definition schema and migrate the `id` parameter of:

- `conjecture-evaluator`
- `proof-engine`
- `proof-reviewer`
- `proof-revisor`

Only the parameter type, conditional paper input, permission line, and path terminology may change in their stored prompts. Their mathematical task instructions and output contracts remain unchanged.

#### MT-2 Markdown branch

If the supplied value ends case-insensitively in `.md` or `.markdown`, the handler must:

- Require a repository-relative path.
- Resolve it beneath `markdown/`.
- Require an existing readable regular file.
- Reject traversal and symlink escape.
- Perform no Markdown syntax, heading, front-matter, math-delimiter, prose-style, or target-identification validation.
- Return a resolved target with `kind = "markdown_file"`, the canonical repository-relative path, and `scope = "whole_file"`.
- Reject a simultaneous `paper` argument.

For now, `markdown/` itself is the research database. No JSON or derived record is created. The handler tells the agent that the complete note is its target and passes the path to that note. The agent must read the whole file needed by its substantive task.

This contract is intentionally coarse. Results may be unreliable when a note contains multiple conjectures or objects, or when no target is clearly identifiable. That limitation is accepted, must be documented, and is not a validation failure. A later design may replace the whole-file path with a reference to a specifically extracted research object.

#### MT-3 TeX-label branch

All other `math_target` values must:

- Match the existing TeX-label key pattern.
- Require a valid explicit `paper` input.
- Trigger construction of a complete label index from every `*.tex` file beneath every discovered paper.
- Use the existing ordinary-comment stripping behavior.
- Include labels in example files, preserving the current recursive scanning scope.

Resolution order is:

1. If any label occurs more than once anywhere across all papers, reject the run and list every duplicate label and every `path:line`, sorted deterministically.
2. If the requested label does not exist, reject the run and state that every discovered paper was searched.
3. If the unique label exists outside the selected paper, reject the run with both the selected paper path and the actual label location.
4. Otherwise return its unique location.

No maintenance or model provider may run after any rejection.

#### MT-4 Runtime target context

The handler must pass one typed target context to prompt rendering and run metadata.

TeX-label example:

```json
{
  "kind": "tex_label",
  "value": "thm:example",
  "path": "papers/example/chapters/result.tex",
  "line": 42,
  "paper": {
    "name": "example",
    "path": "papers/example"
  }
}
```

Markdown-file example:

```json
{
  "kind": "markdown_file",
  "value": "markdown/scratch/idea.md",
  "path": "markdown/scratch/idea.md",
  "line": null,
  "paper": null,
  "scope": "whole_file"
}
```

The resolved context is handler-owned and is not exposed as an additional user parameter.

#### HM-1 Root entrypoint

Root `agent.py` must contain only:

- The import of `metasrc.cli.main`.
- `raise SystemExit(main())`.

It must contain no validation, provider, output, worktree, or maintenance implementation.

| `validation/inputs.py` | Parameter parsing, defaults, typed input and cross-field validation |
| `validation/labels.py` | Paper discovery, TeX comment stripping, global label index |
| `handlers/outputs.py` | Destination resolution, normalization, atomic handler writes |
| `handlers/runs.py` | Run directories, metadata, logs, and report reservation |

### 6.4 Model provider abstraction and permissions

#### PR-1 Provider contract

`providers/base.py` must define equivalent typed contracts for:

```text
ModelRequest
- prompt
- model
- reasoning
- workspace_root
- working_directory
- writable_roots
- output_schema
- run_directory
- stream_output
- enable_event_log

ModelResponse
- final_text
- provider_id
- model
- exit_code
- stdout_path
- stderr_path
- events_path

ModelProvider
- validate(request)
- invoke(request) -> ModelResponse
```

Provider implementations own model-name and capability validation. The orchestrator must not construct Codex-specific flags.

#### PR-2 Existing hosted behavior

`CodexCliProvider` must preserve:

- `gpt-5.6-sol` as the default model.
- Existing reasoning values and default `high`.
- Ephemeral execution.
- Final-message capture.
- Optional JSONL event capture.
- Live stdout and stderr streaming.
- Exit-code and missing-final-message failures.

#### PR-3 Writable roots

The handler and provider adapter must enforce a read-only repository except for canonical roots in `ModelRequest.writable_roots`:

- Green and yellow agents: only `agent-data/`.
- Manuscript-writing red agents: `agent-data/` plus the selected paper directory.
- No model invocation: repository-root write access, another paper, `reports/`, root `README.md`, or `agents/` unless one of those paths is inside an allowed root, which the target layout does not permit.

Approval policy remains `never`, and network behavior remains unchanged from the current risk policy. The provider must reject a missing, non-directory, symlinked, overlapping, or out-of-workspace writable root before maintenance. The resolved paper permission root must equal the paper object selected during input validation.

Yellow repository outputs and green reports remain handler-owned writes performed only after return validation. A model's ability to write `agent-data/` does not authorize it to write its final artifact directly to the handler-owned destination.

### 6.5 `agent-data/` and memory

#### AD-1 Agent-writable area

Every agent receives write permission beneath the active workspace's canonical `agent-data/` directory. `AGENTS.md` must explain that agents may use this directory for task-supporting scratch data, durable memory when the memory protocol applies, and explicitly defined agent state. It must also state that:

- `agent-data/` does not expand a task's final-output contract.
- Agents must preserve unrelated data and follow the ledger protocol for durable memory.
- Scratch files belong under `agent-data/scratch/`.
- Handler-owned reports, README updates, and agent definitions are still returned to the handler rather than written by the model.
- Manuscript-writing agents may additionally edit only their resolved paper directory.

#### AD-2 Memory migration

Move:

- `memory/ledger.yaml` to `agent-data/memory/ledger.yaml`.
- Every registered managed memory file to `agent-data/memory/`.

Update:

- `canonical_entry`.
- `storage.root`.
- Every registered `path`.
- Relevant evidence paths.
- Topology history with one migration event.
- `AGENTS.md` memory entrypoint and command-agent rules.

The existing protocol, record schema, correction history, fallibility rules, and command-agent exemptions remain intact except where the new writable roots make a rule obsolete. Agents modifying durable memory must continue to reread the ledger and affected files immediately before writing; irreconcilable concurrent changes remain a task failure rather than a last-writer-wins update.

### 6.6 Stored prompt migration

#### PI-1 Canonical permission language

Replace the legacy blanket line mechanically. Green and yellow prompts use:

```text
You may write inside agent-data/ and are read-only elsewhere.
```

Manuscript-writing prompts use:

```text
You may write inside agent-data/ and the resolved paper directory, and are read-only elsewhere.
```

These lines describe permissions; the handler and provider enforce them. The stored line need not contain an absolute path. Handler-owned runtime context supplies canonical resolved paths for the active workspace.

#### PI-2 Allowed and forbidden edits

Allowed mechanical edits are limited to:

- The canonical permission line.
- Obsolete `paper/`, `../merge`, and `../style/` references that must point to handler-resolved targets.
- Meta-agent statements that describe the old blanket read-only or fixed-paper policy.
- Parameter declarations, definition descriptions, and `write_scope` metadata needed for `paper_name` and `math_target`.

The following must remain substantively unchanged:

- Agent goals and role.
- Required analysis and evidence.
- Mathematical methods and verdicts.
- Completeness, audit, and build requirements.
- Failure behavior except for new path/input failures.
- Final artifact content and format.

There is no render-time deletion of legacy instructions. Migration edits the stored definitions once, and definition validation rejects the old canonical blanket line afterward. The exact rendered prompt and runtime context remain recorded in the run directory.

#### PI-3 Prompt validation

Definition tests must verify that:

- Every prompt starts with the valid-input line and its new risk-appropriate permission line.
- The legacy blanket read-only line is absent.
- Paper-dependent prompts refer to the resolved paper target and do not contain `paper/` or `papers/template/` as a target path.
- Meta-prompts teach the new permission and resolved-paper rules.
- No unrelated task text changed, using normalized before/after prompt fixtures or an explicit migration allowlist.

### 6.7 Pre-run maintenance

#### MA-1 Generic maintenance contract

A maintenance task returns a structured result equivalent to:

```json
{
  "id": "pdf-cache",
  "status": "updated",
  "started_at": "ISO-8601 timestamp",
  "duration_ms": 124,
  "details": {
    "files": 3,
    "errors": 0
  }
}
```

Allowed statuses are `unchanged`, `updated`, and `failed`. The registry is ordered and extensible without changing provider code.

For every actual provider/model invocation, the orchestrator must:

1. Complete definition, configuration, model, input, cross-field, paper, target, destination, writable-root, and provider-request validation.
2. Construct the final `ModelRequest` and runtime prompt.
3. Create required run logging and metadata state.
4. Run the registered maintenance tasks.
5. Invoke the provider immediately after maintenance.

Maintenance is the final pre-invocation stage. No configuration, input/path resolution, destination validation, provider validation, or request reconstruction may occur between successful maintenance and `ModelProvider.invoke()`. Recording the maintenance result as part of the maintenance stage is allowed.

Each invocation attempt, including each detached job and each batch job, follows this sequence independently. A retry that would start another model process is another invocation and must run maintenance again. Providers must not hide model-process retries from orchestration.

`--help` and `--validate-only` must not run maintenance. A failure before the maintenance stage also does not run it.

#### MA-2 Initial default task

The only initially registered default task is `pdf-cache`. It must call the migrated implementation using the active repository or worktree root and these canonical settings:

```text
root      = <active-workspace-root>
cache_dir = <active-workspace-root>/.pdf-cache
verify    = false
force     = false
prune     = true
```

This is the current implementation's normal incremental mode. It must reuse unchanged path signatures and valid content-addressed objects, avoid re-extraction when the cache is current, and avoid rewriting an unchanged manifest. It must not force overwrite, full verification, or unnecessary regeneration.

The migration should expose a callable API equivalent to `cache_pdfs(root, cache_dir, verify=False, force=False, prune=True)` rather than shelling out to a root script. The module may retain a direct module entrypoint for diagnostics.

#### MA-3 Failure and concurrency

A failed maintenance task must:

- Prevent the model invocation.
- Produce the handler's error exit status, currently 2.
- Record the task, error class, concise message, and duration in the manager log and run metadata.
- Leave any prior valid cache manifest intact through atomic writes.

Parallel invocations targeting the same canonical cache directory must use an interprocess maintenance lock. A waiting invocation acquires the lock and then runs the normal incremental check; it does not assume the preceding result applies. Different worktree roots use their own cache directories and locks.

#### MA-4 Manual command

Expose:

```powershell
python agent.py --maintenance
```

This runs the registered maintenance tasks for the active workspace without invoking an agent or provider. It is not a help-only or validation-only operation.

## 7. Execution Data Flow

### 7.1 Agent invocation

1. Parse CLI arguments and choose the active repository or worktree.
2. Load and validate the agent definition.
3. Parse named and positional parameters.
4. Validate model settings and typed inputs.
5. Discover papers and resolve an explicit paper input when required.
6. Build the global label index only for a label target; resolve the typed mathematical target and enforce its paper cross-field rule.
7. Resolve output destination, working directory, and writable roots.
8. Render stored parameters and append handler-owned resolved paper, target, and permission context.
9. Construct and validate the provider-neutral request.
10. For `--validate-only`, report success and stop without a run directory, maintenance, or provider call.
11. Create the run directory, initial metadata, and logs.
12. Run every registered maintenance task in order.
13. Immediately invoke the selected provider.
14. Validate the returned artifact.
15. Perform the handler-owned atomic output write unless the definition uses direct output.
16. Finalize logs and result metadata.

Help rendering stops after definition/schema information is loaded as needed. It performs no input resolution, maintenance, or provider call.

### 7.2 Manual maintenance

1. Parse CLI arguments and resolve the active repository or worktree.
2. Load and validate the maintenance registry and task configuration.
3. Resolve the canonical cache directory and lock.
4. Run registered tasks in order.
5. Report structured results and return success only if every task succeeds.

No model request is constructed.

## 8. Observable Failure Behavior

| Condition | Required behavior |
|---|---|
| `papers/` missing | Reject any paper-dependent invocation before maintenance. |
| Required paper input omitted | Reject with the agent ID and required `paper` parameter. |
| Selected paper missing or lacks `main.tex` | Reject with the expected `papers/<name>/main.tex` path. |
| Paper name is ambiguous or escapes `papers/` | Reject before prompt rendering and maintenance. |
| Paper-dependent prompt contains a hard-coded `papers/template/` target | Reject the definition. |
| Duplicate label anywhere across papers | Reject every label-target invocation; list every duplicate and all locations. |
| Requested label missing | Reject and report that all discovered papers were searched. |
| Requested label belongs to another paper | Reject with the selected paper and actual location. |
| Label target omits `paper` | Reject as a cross-field input error. |
| Markdown target also supplies `paper` | Reject as a cross-field input error. |
| Markdown path outside `markdown/` | Reject as a containment failure. |
| Markdown file missing or unreadable | Reject before maintenance. |
| Markdown note is unconventional, multi-object, or has no clear target | Accept it as a whole-file target; the documented reliability limitation applies. |
| Maintenance task fails | Do not call the provider; record failure and exit with status 2. |
| Provider attempts a write outside allowed roots | Deny the write through the enforced permission profile; fail the invocation if the task cannot continue. |
| Provider returns an empty result | Preserve the current empty-artifact failure. |
| Generated JSON agent is invalid | Preserve definition-validation failure and do not write it. |
| Concurrent report creation | Preserve atomic report reservation. |
| Concurrent PDF maintenance | Serialize by canonical cache directory, then rerun the incremental check. |

No failure path may invoke a research indexer, local 8B model, watcher, store, or hosted fallback for note processing because none of those components exists in this design.

## 10. Security, Privacy, Performance, and Observability

### 10.1 Security invariants

- Repository root is never a model-writable root.
- `agent-data/` is the only model-writable root common to all command agents.
- A manuscript-writing agent receives exactly one additional root: its explicitly selected paper.
- A model cannot write another paper, `reports/`, root `README.md`, or `agents/`.
- Yellow outputs and green reports remain handler-owned.
- All roots undergo canonical containment and symlink checks.
- Markdown note contents are untrusted repository data and receive no executable or permission semantics.
- Source PDFs remain accessible only through `.pdf-cache/` under the `AGENTS.md` PDF-source policy.

### 10.2 Performance requirements

- Unchanged PDF maintenance remains metadata-fast and does not hash, extract, or rewrite unnecessarily.
- TeX files are read at most once while building a label index for an invocation.
- No label index is built for a Markdown-file target unless another designated validation explicitly requires it.
- No background watcher, local model, note segmentation, topic matching, or generated research database consumes resources.
- Maintenance locking must wait without busy polling and must not corrupt the cache on interruption.

### 10.3 Observability

Run metadata must record:

- Agent and risk.
- Provider and model.
- Active workspace.
- Resolved paper name and path, or `null`.
- Resolved mathematical target kind, path, line, and whole-file scope where applicable.
- Writable roots.
- Maintenance task results.
- Output destination.
- Success or failure.

Manager logs must show maintenance start, result, duration, and failure without duplicating PDF text or Markdown note contents. There are no research-index operational logs.

## 15. Risks

| Risk | Mitigation |
|---|---|
| Copying `template` creates duplicate labels | Every label-target workflow fails clearly until repository-wide duplicates are removed; paper-wide non-label workflows remain usable. |
| A paper input and a label location disagree | Resolve both independently, compare canonical paper identity, and reject before maintenance. |
| Optional `paper` on mathematical agents confuses positional CLI use | Preserve existing parameter order, append `paper`, document named form for label targets, and render generated help from the conditional contract. |
| Whole-file notes contain multiple or no identifiable targets | State the limitation in runtime context and documentation; do not guess or extract an object. |
| Agents overwrite shared memory concurrently | Preserve ledger reread-and-merge rules and fail irreconcilable updates. |
| Writable `agent-data/` is mistaken for permission to change final outputs | Keep task output contracts and handler-owned destinations explicit in prompts, `AGENTS.md`, and provider tests. |
| Custom permission behavior differs across provider versions | Keep the provider adapter responsible for capability validation and prove effective write boundaries with integration tests before acceptance. |
| Mechanical prompt migration accidentally changes task semantics | Use an explicit edit allowlist and normalized before/after fixtures. |
| Maintenance adds latency to every invocation | Retain metadata-fast PDF reuse and serialize only per cache directory. |
| Concurrent maintenance sees a stale pre-lock view | Perform the incremental scan after lock acquisition. |
| Runtime prompt context obscures stored text | Save the exact rendered prompt and resolved context in the run directory. |
