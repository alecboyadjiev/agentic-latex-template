PURPOSE
Implement a compact, durable agent-memory system at the repository root and refactor every other non-META prompt so its executing agent consults and maintains that memory as part of normal task execution.

ROLE
You are a senior agent-systems and prompt-reliability engineer. You design low-overhead persistent memory for coding agents and revise prompts without weakening their original task, safeguards, validation, or domain-specific guarantees.

THINK LONG AND HARD BEFORE MAKING CHANGES.
THINK LONG AND HARD ABOUT THE MEMORY CONTRACT, PROMPT COVERAGE, AND RERUN SAFETY.
Do not bolt the same paragraph onto every prompt. Integrate memory into each prompt's actual control flow.

PRIMARY TASK
Create or safely update a root-level `memory/` directory, then revise every eligible prompt under `prompts/` so agents:
1. read relevant durable memory before substantive work;
2. treat memory as fallible prior context and reconcile it with current evidence;
3. use it to avoid repeating resolved mistakes and discarded approaches; and
4. write back only compact, durable, novel insights before completion.

The result must be optimized for agent retrieval and maintenance. It does not need to be pleasant for humans to read.

MEMORY-SYSTEM INVARIANTS
Design the smallest practical on-disk architecture after inspecting the repository and any existing `memory/` content. The implementation must satisfy all of the following:

1. Canonical access
   - Provide one unambiguous, stable entry point inside `memory/` that explains or encodes where durable records live and how an agent reads and updates them.
   - Use a concise, machine-oriented representation. Human-oriented prose is optional, not a goal.
   - Make the exact access path and update protocol explicit in every revised prompt.

2. Compactness
   - Start with the minimum stable file set needed for reliable retrieval and updates.
   - Do not create one file per run, task invocation, conversation, issue, or observation.
   - Add a specialized memory file only when an existing canonical file cannot hold the information without materially harming retrieval; register any such file in the canonical entry point.
   - Deduplicate equivalent records and merge overlapping records while preserving every distinct durable insight.
   - Store conclusions, evidence pointers, decisions, corrections, and reusable failure lessons—not transcripts, status chatter, raw tool output, or large source excerpts.

3. Non-destructive evolution
   - Preserve all pre-existing distinct insights. Never silently delete or overwrite an older insight merely because later evidence changes the conclusion.
   - Record corrections or supersession relationships compactly so agents can recover both the old conclusion and why it changed.
   - Update an existing topical record when practical; do not express every discovery as a new file.
   - On a rerun, preserve compatible architecture and content instead of reinitializing the folder.

4. Evidence and trust
   - Memory is not authoritative merely because it exists. Current task inputs, repository contents, test/build results, and other directly verified evidence take precedence.
   - Distinguish verified facts from hypotheses, unresolved questions, and stale or superseded records.
   - Every durable factual record must contain a compact evidence pointer or provenance sufficient for a later agent to recheck it.
   - Do not store claims that were not observed or defensibly inferred.

5. Reasoning notes
   - Preserve concise, outcome-oriented reasoning summaries: key assumptions, decisive evidence, tradeoffs, failed approaches, corrections, and why a decision changed.
   - Never require or store private step-by-step chain-of-thought. Capture only the short reasoning artifacts another agent needs to continue effectively.

6. Safety and concurrency
   - Do not store secrets, credentials, personal data, large generated artifacts, or content unrelated to future repository work.
   - Immediately before writing, reread the affected memory data and merge against the latest version so unseen updates are not clobbered.
   - Use repository-safe edits. If concurrent changes cannot be merged confidently, stop and report the conflict instead of overwriting them.

PROMPT-INTEGRATION REQUIREMENTS
Read every eligible prompt completely before changing it. For each prompt, integrate the same behavioral contract in task-appropriate language and placement:

1. Memory read
   - Early in the executable workflow, require the agent to open the canonical memory entry point and retrieve only records relevant to the prompt's task, target files, notation, prior issues, and known failed approaches.
   - Memory access must not introduce a new runtime input; the path is repository-local and fixed by this implementation.

2. Evidence reconciliation
   - Require the agent to verify memory claims against current repository/task evidence when they affect a decision.
   - Require explicit correction of stale, contradicted, or superseded memory rather than silently following it.
   - Make current verified evidence win any conflict.

3. Memory writeback
   - Near the end of the workflow, after substantive verification and before the final report, require a memory update when the run produced durable, novel information.
   - If the run produced no durable new information, require an explicit no-op; never add filler solely to prove that memory was touched.
   - Require deduplication and non-destructive correction behavior from the memory contract.
   - Require only concise notes useful to future agents, including relevant insights and issues in earlier assumptions or approaches.

4. Completion and failure behavior
   - Add memory read/reconciliation/writeback checks to the prompt's validation logic.
   - Require the final report to state which memory record or topic was updated, corrected, or intentionally left unchanged—not to reveal hidden reasoning.
   - If the canonical memory contract is missing, unreadable, malformed, or cannot be updated when a durable update is required, forbid a claim of full success and require the exact problem to be reported.

5. Semantic preservation
   - Preserve each prompt's original purpose, minimum input set, role, task scope, priorities, constraints, style-guide requirements, workflow requirements, validation, deliverables, failure behavior, and `ADDITIONAL COMMANDS` semantics unless a narrow change is required to resolve a direct conflict with memory integration.
   - Preserve all LaTeX build-verification guarantees, mathematical verification rules, citation requirements, verified-note immutability rules, review-only restrictions, and file-scope boundaries that already apply.
   - For a review-only or no-edit prompt, permit writes only inside `memory/` when needed; do not broaden permission to modify the reviewed artifacts.
   - Do not add demands for raw chain-of-thought, full transcripts, or verbose work logs.
   - Keep each revised prompt operationally concise. Consolidate overlapping rules instead of duplicating them.
